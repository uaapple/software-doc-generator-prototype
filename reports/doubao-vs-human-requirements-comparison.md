## 总体结论

本次 Doubao 生成结果已经能够抓住“扭矩干预、优先级、安全功能、边界限制、接口信号、激活状态”等核心主题，但输出形态仍然明显偏向“平铺的软件需求条目”，还没有对齐到人工样例的“章节化软件设计需求”风格。

和人工样例相比，当前生成结果的主要问题不是“完全没抓到内容”，而是：

- 没有生成 `3.31 -> 3.31.1 / 3.31.2` 这种章节结构
- 没有把前轴 / 后轴做成对称展开
- 没有稳定生成“激活标志位判断”和“扭矩计算逻辑”这两类设计需求条目
- 没有形成 `SMiVCU-10160 / 10597 / 10161 / 10598` 这种内部引用式写法
- 更像“需求摘要列表”，而不是“可直接进入详细设计文档的条目”

## Doubao 输出条目逐项观察

### 1. `SWR-001 ESC扭矩干预请求优先级处理`

命中点：

- 抓到了系统需求中的主优先级：前轴升扭、前轴降扭、主动制动、VLC、RBS
- 抓到了“无主动安全功能激活且 ESC 未干预时，目标扭矩为扭矩分配后的扭矩”

问题：

- 把多个原本应该拆开的设计逻辑揉成一条
- 没有前轴/后轴分章
- 没有信号级别的变量承载，如 `ESCWhlTq_tqTarFrntAxle`

### 2. `SWR-002 主动安全功能激活时扭矩仲裁`

命中点：

- 正确抓到了 `AEB/ABS/CDP` 优先于 `DTC/ASR/VDC`
- 正确保留了 `DTC > ASR > VDC`

问题：

- 这是对系统需求的归纳性改写，不是人工样例中的详细设计条目
- 没有进入前轴/后轴扭矩计算分支

### 3. `SWR-003 主动安全功能激活/退出时扭矩变化率控制`

命中点：

- 准确覆盖了 `SMiVCU-4487`

问题：

- 这条更接近系统需求复述
- 在人工设计样例中，这类逻辑并没有作为本次目标样例的主要章节展开

### 4. `SWR-004 ESC前后轴扭矩干预激活标志位判断`

命中点：

- 已意识到“激活标志位判断”是一个独立需求主题
- 也意识到条件来源包括升扭、降扭、RBS、ISA/CCO

问题：

- 前后轴被合并
- 条件表达还不够像人工样例那样精确、逐项、可追溯
- 没有按前轴/后轴分别保留信号名

### 5. `SWR-005 ~ SWR-010`

这些条目包括：

- 接口信号定义
- 扭矩边界限制
- 仅 RBS 激活状态
- 越野 TCS 激活状态
- 执行周期
- 扭矩请求有效性校验

评价：

- 从“通用软件需求生成”的角度，这些条目不算坏
- 但从“对齐当前人工目标样例”的角度，这些内容偏散，且不少条目并不属于本次目标输出的核心结构
- 也就是说，模型在“挖更多可能有价值的需求”，而不是“严格复现人工样例的设计文档结构”

## 核心差距总结

### 1. 结构差距最大

人工样例是：

- `3.31 扭矩干预功能`
- `3.31.1 ESC前轴扭矩干预`
- `3.31.2 ESC后轴扭矩干预`

Doubao 当前输出是：

- `SWR-001` 到 `SWR-010` 的平铺清单

这说明当前系统虽然有“写作规则”，但主生成链路依然受到旧 `requirements[]` schema 的约束，模型被鼓励输出“条目列表”，而不是“章节化设计文档”。

### 2. 粒度差距明显

人工样例按“一个设计主题一条需求”拆分得很细，例如：

- 前轴激活标志位判断
- 前轴扭矩计算
- 后轴激活标志位判断
- 后轴扭矩计算

当前生成则偏向把多个逻辑主题做摘要式合并。

### 3. 对称展开能力不足

人工样例非常强调前轴/后轴成对写法。  
当前生成虽然理解“有前后轴”，但没有形成稳定的对称输出结构。

### 4. 设计化表达不足

人工样例是“设计需求”：

- 有变量
- 有模式
- 有条件分支
- 有内部引用
- 有边界限制注释

当前生成结果更多是“系统需求 + 代码信息”的整合性描述。

## 这次试跑里 Doubao 做得好的地方

- 能稳定抓到系统需求里的主控制目标
- 能抓到主动安全优先级
- 能从模型代码和 PDF 中带出信号名、边界限制和状态位
- 来源追溯是有的
- 没有明显胡编乱造冲突项

## 这次试跑里最需要改进的方向

### 1. 先改输出协议

如果仍然要求模型输出当前这种平铺 `requirements[]`，它就很难自然生成人工样例那种章节化软件设计需求。

### 2. 强化“按目标样例复现结构”的 few-shot

目前 active skill 已经加入了领域知识，但主生成 prompt 还不够强地要求：

- 先分章
- 再分前轴/后轴
- 再拆激活逻辑 / 计算逻辑

### 3. 增加 benchmark 量化评估

这次最适合继续做的，不是只肉眼看，而是把这组样例正式录成 benchmark case，然后用系统自动算：

- `section_structure_score`
- `requirement_coverage_score`
- `logic_branch_score`
- `signal_reference_score`
- `traceability_score`
- `writing_quality_score`

## 建议的下一步

1. 把这组样例录成 benchmark case，拿人工样例作为 `golden`
2. 跑一次 skill refinement 的基线评估，得到当前 active skill 的量化分数
3. 基于这次差距，继续强化：
   - 输出结构
   - 前后轴对称规则
   - 激活标志位 / 扭矩计算两类条目的拆分规则
4. 再重跑 benchmark，观察分数是否提升

## 简短判断

当前结果可以认为是：

- “内容方向基本正确”
- “设计文档形态明显不对”

离人工样例的距离，主要在“结构和粒度”，不在“完全没理解业务”。
