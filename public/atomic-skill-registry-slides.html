Atomic Skill Registry

原子化 Skill Registry

把当前 skill 系统从“按文件/盒子管理规则”升级成“按原子 skill item 管理，再由 item 物化回文件”的统一模型， 同时让 docType 正式成为一等公民。

01

Problem Framing

现状的问题，不在“规则不够多”
而在“规则不可精准管理”

把“文件”当主对象，会让 review、proposal、replay 都变粗。

Current

按文件/盒子管理

  • 一个 markdown / JSON 里混着很多不同粒度的规则与样例。
  • 只能对整段文本提案，难以精确命中某一个 skill。
  • docType 只像 overlay，不是完整 profile。
  • 回放与 fallback 容易退化成“补整段文件”。
  • 历史 rule 追溯、审核、排序、废弃都很难稳定编号。
Target

按原子 skill item 管理

  • 每条 skill 都有稳定的 skillCode。
  • 每条 skill 独立 review、独立 proposal、独立 provenance。
  • 所有层级都统一成 profile + items 结构。
  • replay / refinement / fallback 直接指向具体 item。
  • markdown 和 domain-knowledge.json 变成物化产物。
核心变化：把“文件”从真相源降级为“展示/物化结果”。 观众要记住的第一件事：主对象从 file 变成 skill item。
02

Mental Model

统一成“Profile 盒子 + Skill Item 原子”

Profile = 盒子

{
  "layer": "docType",
  "profileKey": "detail_design",
  "displayName": "详细设计",
  "documentTypeScope": "detail_design",
  "status": "active"
}
盒子定义边界
层级、作用域、profile key、状态
Item 承载具体 know-how
写作规则、样例、蓝图、source policy、priority
Loader 按层叠加
generic → docType → domain → module

Skill Item = 原子对象

{
  "skillCode": "DOC-detail_design-rule_hint-001",
  "layer": "docType",
  "profileKey": "detail_design",
  "kind": "rule_hint",
  "title": "先描述结构分解再下钻",
  "content": "章节骨架优先于局部细节",
  "order": 10,
  "status": "active"
}

为什么这很重要

  • 编号稳定，新增只增不复用，重排不改号。
  • 任何提案都可以说清楚“改哪条”。
  • 每条 item 都能追溯来源 case / proposal / legacy rule。
  • 同一 profile 下，删除或废弃某条 item 不影响其他 item。
03

Layer Strategy

四层范围明确覆盖，docType 这次不再缺席

generic
与 domain、module、docType 都无关的通用写法。
跨上下文复用
docType
体裁规则、章节结构、HIL preconditions/steps/expected results。
优先判定 一等公民
domain
如 embedded_vcu 的共享控制逻辑、风格和术语约束。
共享 know-how
module
对象专有、信号专有、骨架专有、蓝图专有，强绑定当前模块。
最具体层

判定优先级

先判 docType，再判 domain，再判 module，只有完全跨上下文时才是 generic。

04

Schema & Numbering

对象设计要点：稳定编号、结构化 payload、可追溯 provenance

Skill Code 规则

  • 格式固定：<layer>-<profile>-<kind>-NNN
  • 示例：DOC-detail_design-rule_hint-001
  • 用户可见、提案可引用、review 可复制。
  • 新增 item 只增不复用，重排不改号。

Provenance / Review 记录

  • createdFromCaseIds
  • createdFromProposalId
  • legacySource
  • migratedFromRuleId
  • 最近一次审核信息单独存放
文本类

content

适合 writing_rule / extraction_rule / validation_rule / examples。

结构化类

structuredPayload

适合 alias、normalization、forbidden expansion、blueprint policy。

排序与状态

order + status

支持独立移动顺序、草稿、启用、废弃，而不干扰同 profile 其他 items。

06

Skill Management

管理界面从“编辑 profile”升级到“逐条管理 skill item”

第一层

Layer

generic / docType / domain / module

第二层

Profile

按 profileKey 打开某个盒子，如 detail_design、embedded_vcu。

第三层

Skill Items

每条 item 显示 skillCode / kind / title / status。

交互要求

  • 单条打开、编辑、删除、排序。
  • 按 layer / profile / kind / documentType 过滤搜索。
  • 复制 skillCode 作为 review / replay / proposal 引用。
  • 从 item 反查来源 case、proposal、最近修改、所属 profile。

08

Replay & Fallback

驳回后的修复提案，必须精准命中某一条 skill

Material Pack 需要增强

  • 当前 rejection 的 targetArea
  • 当前 documentType
  • 当前 module / domain / profile 上下文
  • 候选 target skill items 列表及 relevance explanation

Fallback 固定策略

先找高匹配 item
找到就走 modify_skill_item
找不到合适 item
才走 add_skill_item
禁用旧退路
不允许直接退回“补整段文件”模式

HIL 驳回

优先命中 docType: hil_test_case

详细设计结构驳回

优先命中 docType: detail_design

VCU 共享控制逻辑驳回

优先命中 domain: embedded_vcu，模块专属才下沉到 module

09

Registry Index

SkillRuleService 升级成 Skill Registry Index

新职责

  • 从 skill-items.json 建立 item index。
  • 按 layer/profile/kind/skillCode 检索。
  • 为 replay/refinement 提供候选 target skill items。
  • 把 registry 物化回 markdown / domain-knowledge.json。

兼容策略

  • 旧 ruleId 保留在 provenance.migratedFromRuleId。
  • 老逻辑通过映射层找到对应 skillCode。
  • 新 proposal / review / apply 一律以 skillCode 为准。

一句话理解

从“解析文件拿规则”转成“以 registry 为中心做索引、检索、物化和兼容映射”。

10

Migration Strategy

迁移不是大爆炸重写，而是“导入 → 标注 → 审计 → 回迁”

阶段 1

导入

把 markdown rules、examples、generationPriorities、ruleHints、antiPatterns、source policy、blueprint 全部拆成 items。

阶段 2

标注

为每个导入 item 写入 skillCode、legacySource、migratedFromRuleId、migrationBatchId。

阶段 3

审计

重点找 generic 污染、应提升到 embedded_vcu 的共享项、应进入 docType 的项、多 profile 重复项。

阶段 4

受控回迁

优先处理高置信迁移：HIL / detail design 提到 docType，VCU 共享写法提到 domain，模块骨架保留在 module。

11

Test & Assumptions

落地验收标准：能逐条管、能精准命中、能稳定回物化

核心测试点

  • 新增一个 module item 后，可单独查、改、删、排，不影响同 profile 其他 items。
  • docType 下 items 能独立编号、独立查看、独立修改。
  • replay / fallback 能命中具体 skillCode。
  • 没有命中时，会生成 add_skill_item 并写清目标 layer/profile/kind。
  • materialize 后 markdown 和 domain-knowledge.json 与 registry 一致。
  • loader 仍按 generic → docType → domain → module 合成。

关键假设

  • skill-items.json 是 canonical source。
  • skillCode 是后续 proposal / review / replay 的主编号。
  • docType 本次与其他层同级纳入全链路。
  • 历史资产按“导入 + 审计 + 分阶段回迁”推进，不做一步到位重写。
  • 当前主要 domain 是 embedded_vcu，但 schema 允许未来扩展。

观众带走的结论

这次改造的本质，不是再加一层配置，而是把 skill 从“文件里的文本块”升级成“可编号、可提案、可追溯、可物化的原子对象”。
