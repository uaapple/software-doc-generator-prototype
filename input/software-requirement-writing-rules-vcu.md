# 嵌入式VCU软件需求撰写规范总结

## 文档信息

- 文档类型：撰写规则
- 领域：嵌入式 VCU 软件需求
- 语言：中文
- 版本：v1
- 来源：工程师提供的现行撰写规则，人工整理为结构化文档
- 整理日期：2026-04-04

## 1. 结构规范：层次清晰，模块化

### 1.1 分级标题

- 使用多级标题明确功能模块的从属关系，便于导航和管理。
- 使用形式可参考 `3.31 -> 3.31.1`。
- 父子功能关系需要在标题层级中体现。
- 标题命名应便于定位模块边界和上下级关系。

示例：
“扭矩干预”是父功能，“ESC前/后轴扭矩干预”是其子功能。

### 1.2 功能隔离

- 将紧密关联但物理对象不同的需求拆分为独立子章节。
- 相似对象的章节结构应尽量对称。
- 拆分后的章节应支持独立开发和独立测试。

示例：
前轴需求与后轴需求拆分为独立子章节。

## 2. 描述方式：结构化与条件化

### 2.1 激活/判断逻辑

- 优先采用“当满足以下任一条件…，否则…”的句式。
- 条件项使用 `1, 2, 3` 等分点列出。
- 显式写明逻辑关系，例如“与”“或”。
- 逻辑表达应无二义性。

### 2.2 计算与仲裁逻辑

#### 2.2.1 明确优先级

- 多源请求仲裁时，需要直接声明优先级顺序。
- 推荐句式：“优先级顺序为：X > Y > Z”。
- 优先级关系必须完整且不可省略。

#### 2.2.2 分情况阐述

- 使用“当…时，输出=…”的句式。
- 覆盖全部主要输入组合与输出路径。
- 避免遗漏默认路径或兜底行为。

#### 2.2.3 定义边界

- 对激活等状态给出明确阈值。
- 对区间范围给出上下边界及包含关系。
- 避免使用模糊区间描述。

示例：
大于低阈值且小于等于高阈值。

## 3. 接口与数据定义：精准明确

### 3.1 信号命名规范

- 所有输入输出信号名称应具备自解释性，并体现来源或类型。
- 命名应能让读者快速识别信号用途和来源。
- 避免无语义缩写或无法追溯来源的命名。

#### 3.1.1 输入信号

- 优先体现来源系统标识。
- 可使用来源系统前缀，例如 `ESC_`、`EHB_`。
- 前缀应与实际来源系统保持一致。

示例：
`ESC_` 开头表示来自 ESP，`EHB_` 表示来自电子液压制动系统。

#### 3.1.2 内部信号/变量

- 在括号内注明内部变量名。
- 补充变量用途说明，例如“内部使用”。

示例：
`ESCWhlTq_tqTarFrntAxle`（内部使用）。

### 3.2 数值明确

- 枚举值和状态值需要给出具体定义，不能只写名称。
- 明确列出取值与语义映射。
- 必要时使用十六进制或约定编码表示状态。

示例：
`0x1: Active, 0x3: ESPCtrlSplt`

## 4. 可追溯性与一致性

### 4.1 内部引用

- 通过引用同一文档内的其他需求项避免重复定义，并维持需求一致性。
- 优先复用既有需求定义，不重复展开已有概念。
- 引用时应保留需求编号。
- 被引用项与当前需求之间的依赖关系应清晰可见。

示例：
引用 `(SMIVCU-10160)`、`(SMIVCU-9477)` 等需求项。

### 4.2 外部系统联动

- 需求中应明确与外部系统或功能的交互条件。
- 说明与 `ESC`、`ADAS` 等系统功能的交互条件。
- 确保系统边界和协同关系可追踪。

## 5. 可测试性

### 5.1 每条需求应可验证

- 每条需求应天然对应可执行或可设计的测试场景。
- 激活判断类需求应支持通过输入组合验证输出状态。
- 计算与仲裁类需求应支持按优先级分支设计测试用例。
- 需求表述应足够明确，使测试预期可判定。

示例：

- 通过不同输入条件组合检查输出标志位是否符合预期。
- 为每个优先级分支和计算路径设计测试用例，验证输出扭矩值是否正确。

## 6. 非功能性约束

### 6.1 安全与边界处理

- 通过补充说明明确最大/最小限制等安全边界。
- 边界限制可通过“注”等补充说明形式给出。
- 安全约束应明确、可验证、不可省略。

## 提炼后的总原则

- 结构需要清晰分层，支持模块化维护。
- 描述方式要结构化、条件化、无歧义。
- 接口和数据定义必须精准明确。
- 需求之间需要可追溯且保持一致。
- 每条需求都应具备可测试性。
- 安全边界和非功能约束需要显式写出。
