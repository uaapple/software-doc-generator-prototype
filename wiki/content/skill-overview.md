# Skill 概览

## 这页讲什么

这页专门回答 3 个问题：

- 什么是工程里所说的 `skill`
- `skill` 和 LLM 在生成文档时是怎么配合的
- 当前系统里的 `skill` 大致分成哪些类目

如果你已经在页面里见过 `Atomic Skill`、`fallback`、`技能工单`、`targetArea` 或各种 `kind`，但还没把这些概念连起来，这页就是给你看的。

## 什么是 skill

在这个工程里，`skill` 不是一个“会自己跑起来的小程序”，更接近一套可持续维护的生成经验和约束集合。它把人希望系统长期遵守的东西沉淀下来，例如：

- 哪些事实更重要，应该优先抽
- 某类正文应该怎么写，哪些写法不要出现
- 某些术语、信号名、别名之间应该怎样对应
- 哪些内容属于常见错误，后续应当主动拦住

所以可以把 `skill` 简单理解成：

- 它不是一次性的 prompt 临时描述
- 它也不是最终文档正文
- 它是夹在“输入证据”和“生成结果”之间的一层长期规则与知识

## skill 在系统里的作用

如果没有 `skill`，LLM 更容易把每次任务都当成一张“从零开始回答”的新卷子。这样虽然也能生成内容，但稳定性会比较差，容易出现这些问题：

- 同一种主题，这次和下次写法不一致
- 某些模块边界总是写得过宽或过窄
- 术语、信号名、章节组织方式来回漂移
- 某些历史上已经被驳回过的问题反复出现

`skill` 的作用，就是把这些“已经知道该怎么做、或者已经知道不要怎么做”的经验固定下来，让后续生成不必每次从头猜。

## skill 和 LLM 是怎么配合的

可以把两者的配合关系理解成一句话：

- `skill` 负责给边界、给规则、给上下文
- `LLM` 负责在这些边界内组织表达、补全结构、产出结果草稿

更具体地说，生成链路里大致是这样协作的：

1. 系统先从当前模块资产里抽取候选证据。
2. 后端根据当前文档类型、模块上下文和 active skill，挑出相关规则、样例和知识项。
3. 这些 skill 内容和证据一起进入后端编排层。
4. LLM 不直接“自由发挥”，而是在已有事实、模板和 skill 约束下组织输出。
5. 生成后的结果再经过校验、审核和驳回链路，必要时把新问题继续沉淀回 skill。

这也是为什么系统里经常会出现“生成 -> 驳回 -> Replay -> 技能工单 -> skill 更新 -> 再生成”的闭环。  
LLM 负责一次次产出，`skill` 负责把每次修正沉淀成长期能力。

## skill 和普通 prompt 的区别

很多人第一次接触时，会把 `skill` 理解成“更长一点的 prompt”。两者确实有关，但不完全一样。

`skill` 更强调的是可维护、可归类、可复用：

- 它会按 layer 和 kind 组织，不是随意堆在一段提示词里
- 它可以被审核、驳回、回投和工单化处理
- 它会随着历史问题持续演化，而不是只服务一次任务

所以更准确地说，`skill` 是系统长期能力的一部分，prompt 只是它被送入模型时的一种承载方式。

## skill 类目怎么理解

系统里的 `skill` 至少有两层分类方式要一起看：

- `layer`
  表示这条能力影响范围有多大
- `kind`
  表示这条能力本质上在干什么

先理解这两层，再看页面上的各种字段会轻松很多。

## 四层 layer

当前系统主要有 4 层：

- `generic`
  作用范围最宽，适合放通用写作约束、通用抽取原则、通用术语规则。
- `docType`
  面向某一种文档类型，例如软件需求、详细设计、HIL 测试用例。
- `domain`
  面向某个业务域或专题领域，例如某类控制域、平台域。
- `module`
  面向最具体的功能模块，适合沉淀只对当前模块稳定成立的经验。

可以把它们理解成从“全局”到“局部”的 4 个层级。

## 常见 kind 类目

下面这些 `kind` 是你在技能管理、Replay 或工单里最常见的几类：

### `writing_rule`

约束正文怎么写。它解决的是写法、粒度、组织方式和表达边界。

### `extraction_rule`

约束先抽什么事实。它解决的是生成前的证据组织问题。

### `validation_rule`

约束什么结果算合格。它更偏“拦错”和“补边界”。

### `good_example` / `bad_example`

分别提供正例和反例，帮助系统更稳定地贴近目标写法，或避开已知坏写法。

### `generation_priority`

告诉系统在多类信息并存时，哪些主题、结构或事实应当优先进入结果。

### `rule_hint`

提供更轻量的提示性知识，例如适用领域、章节提示、目标风格或来源依据。

### `anti_pattern`

沉淀“常见错误模式”，提醒系统不要重复犯同一类错。

### 知识类 kind

这些更偏领域知识和命名规则：

- `source_alias`
- `code_style_prefix`
- `forbidden_expansion`
- `normalization_rule`
- `source_policy_setting`
- `document_blueprint_section`
- `document_blueprint_policy`

这类项不一定直接决定某一句正文怎么写，但会影响术语统一、章节组织、可接受扩写范围和蓝图结构。

## 为什么 skill 会不断变化

因为它本来就不是一次定义完毕的“静态说明书”，而是系统能力的沉淀层。

当你在结果审核里发现问题时，常见的后续动作不是只改这一次结果，而是继续问：

- 这是输入没覆盖，还是 skill 没覆盖
- 这是该补规则、补样例，还是补领域知识
- 这条经验应该沉淀到哪一层，避免以后重复出错

所以 skill 的变化，通常意味着系统在把一次具体问题转成后续可复用的能力。

## 使用者需要记住什么

如果你不是维护 skill 的同学，也不必记住每个字段细节。先抓住下面 3 件事就够了：

1. `skill` 是系统长期生成能力的一部分，不是一次性的说明文本。
2. `skill` 和 LLM 不是替代关系，而是“规则层 + 生成层”的配合关系。
3. 当你看到 fallback、Replay、技能工单时，本质上是在帮助系统把新经验继续沉淀回 skill。
